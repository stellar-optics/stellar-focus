# Table-driven golden tests

`golden.Case` groups one actual XDR value with the golden-file name,
description, and any assertion options that apply only to that case.
`Golden.AssertAll` and `Golden.AssertAllParallel` compare a table against its
fixtures and report every result with its row number and name.

See the implementation in
[`pkg/golden/golden.go`](../../pkg/golden/golden.go) and its concise package
overview in [`pkg/golden/README.md`](../../pkg/golden/README.md).

## Build a table

Set the fixture directory once with `golden.WithDir`; each `Case.Name` is
relative to that directory and does not include the `.golden.json` suffix.
`Value` is the actual XDR value generated by the test. `Description` explains
the case in a failure summary and is written into a newly recorded fixture.
`Options` adds `focus.Option` values for that row; suite-wide options can be
set on `golden.New`.

```go
func TestPaymentVariants(t *testing.T) {
    g := golden.New(t,
        golden.WithDir("testdata/payments"),
        golden.WithOptions(focus.WithDiffContext(2)),
    )

    cases := []golden.Case{
        {
            Name:        "native_payment",
            Value:       buildNativePayment(), // this test's XDR builder
            Description: "native payment to the primary recipient",
        },
        {
            Name:        "credit_payment",
            Value:       buildCreditPayment(),
            Description: "issued-asset payment",
            Options:     []focus.Option{focus.WithMaxChanges(8)},
        },
    }

    g.AssertAll(cases)
}
```

The builder functions stand for the application's own transaction-building
code; each must return an XDR value accepted by focus. To create or deliberately
update the fixtures, run the test with:

```sh
go test ./... -focus.update
```

Review the resulting fixture diffs before accepting them.

## Sequential and parallel tables

`AssertAll` is sequential. It runs every row even after a failure, so one
invocation reports the whole table rather than stopping at the first drift.
Use it for ordinary tables, or when row execution has side effects that should
not overlap.

`AssertAllParallel` runs each row in its own goroutine and collects and reports
results in table order. Use it when rows are independent and the fixture suite
is large enough to benefit from concurrent comparisons:

```go
g.AssertAllParallel(cases)
```

The parallel runner does not promise that row work finishes in input order.
Do not use it if the code that builds or compares the values has shared mutable
state or depends on execution order.

## Read the failure summary

A drifted row includes its one-based position, name, and (when provided)
description. The summary table also distinguishes drift from a missing file
and can list differing field paths:

```text
golden: table summary — 5 case(s), 1 failed:
  [1/5] payment_v1: ok
  [2/5] payment_v2: DRIFTED (new fee calculation)
  [3/5] payment_v3: ok
  [4/5] payment_v4: ok
  [5/5] payment_v5: ok

FAILED GOLDEN FIXTURES (1 / 5):
┌─────────────────────┬─────────┬───────────────────────┐
│ Fixture Name        │ Status  │ Differing Field Paths │
├─────────────────────┼─────────┼───────────────────────┤
│ payment_v2          │ DRIFTED │ Fee                   │
└─────────────────────┴─────────┴───────────────────────┘
```

The index is one-based. The runner reports all rows, and the final diagnostic
includes the relevant XDR diff; use `-focus.update` only when that change is
intentional.
